## Frozen ports for B and S4

Serializable types are in `kinewright_project::studio_records`; runtime handles and owner methods are in `studio_store`. The fixture protocol is serde JSON with unknown-field refusal, distinct opaque IDs and exact `ObjectRef { sha256, byte_length, record_kind }` values. `ja_s3_store` and `ja_s3_host` exercise the receiving fixtures without Studio, Whisper or a scheduler.

- `SnapshotKey { project, version, head, document_hash, input_manifest_ref }` binds immutable identity. `PublishSnapshot` adds the exact indexed `checkpoint_ref`, expected head, optional parent/run provenance and revision refs. `SnapshotDescriptor` retains checkpoint/document/lineage/input/revision refs. `FrozenContext` contains the pinned descriptor, document, certified input leases and LUT/font resource context.
- `FeedbackAnchor` binds snapshot, integer frame, rational fps, raster/orientation and optional occurrence/source/beat target. `FeedbackRevision` retains its predecessor, original text, strokes and frame-proof refs. Strokes use the existing bounded JSON point-pair representation in normalized displayed-image coordinates. `VoiceRef` retains NoteId, audio ref, duration in microseconds, optional audio range/playhead log, original ASR and chosen transcript revision. JobId is distinct. Mapping and note execution remain B's C4/C5 work.
- `FeedbackBatch { batch_id, revision_refs }` freezes exact selected revisions. `ReviseRequest { command_id, batch_id, expected_candidate_head }` is durable with it. `PinnedSubmittedBatch` includes those revisions, the original request and consumed-by RunId. Producer/agent reads use submitted batches; saved unsubmitted revisions remain private. Without S4, submission returns Waiting.
- `ResolveFeedback { comment_revision_ref, candidate_checkpoint_ref, beat_map_ref }` and `CommentResolution { original_ref, candidate_head, temporal, spatial, evidence_refs }` freeze B's mapping ports. Temporal statuses are Exact, Mapped, Ambiguous, Removed and Unresolved; spatial statuses are Exact, Transformed, Unresolved and Removed. `Disposition` retains original/resolution refs, optional resulting snapshot, outcome, optional reason and evidence. C1 supplies these DTOs without mapping execution.
- Both `ProjectBundle` and `Ja1EditingSession` expose `metadata_command(&MetadataEnvelope, MetadataScope, &MetadataUpdate) -> ReceiptLookup`, `read_snapshot(&SnapshotKey) -> PinnedSnapshot`, `read_feedback(&ObjectRef) -> PinnedFeedback`, and `read_submitted_batch(&FeedbackBatchId) -> PinnedSubmittedBatch`. The session also exposes `issue_metadata_issuer`, `metadata_envelope(CommandId)`, `metadata_generation` and `reconcile_metadata`.
- `MetadataEnvelope { id, project_id, target_branch, owner_epoch, expected_head }` and `MetadataUpdate { expected_root_generation, change }` bind the complete typed request into the existing command digest. Changes are PublishSnapshot, SaveFeedback, SaveVoice, SubmitBatch and Orchestration. Scope/project checks precede receipt replay. Fresh rebases require new IDs. Callers cannot supply index root pointers. Metadata uses durable history and never installs or resumes manual Core.
- Domain scopes are `MetadataScope::{Feedback, Snapshot, Orchestration}`. The committed receipt carries `ReceiptResult::Metadata { result }`, where `MetadataResult` is Snapshot(SnapshotKey), Feedback(ObjectRef), Voice(NoteId), Batch(FeedbackBatchId) or Orchestration(Vec<RunId>). `SubmitBatch { batch, request }` freezes both values; `Orchestration { runs, consume_batch: Option<(FeedbackBatchId, RunId)> }` uses the validated H1 port. `HostReply.metadata` carries the receipt. Its `revise_result` is Waiting with a reason while S4 is absent; Accepted contains RunId/FeedbackBatchId, and Conflict remains distinct.
- H1 uses `validate_run_update(envelope, update) -> ValidatedRunUpdate`, then `commit_orchestration(envelope, transition) -> OrchestrationReceipt`. The validated type has private fields. Both owners and the session free-function adapter expose the commit port. The receipt retains the original command receipt, run IDs and consumed-batch linkage. Run and feedback consumption publish atomically. Seven registered payload kinds cover snapshots, event segments, effects, requests, deliveries, results and usage. ClaimIndex and CreationBrief remain unsupported and refuse.
- `RunView`, `RunEvent` and `RunIntent` preserve separate phase/outcome/wait/cleanup facts and opaque control revision. Pages have 200-row and 8 MiB bounds. The receiver disables controls after gaps or invalid events until refresh, refuses stale controls, and suppresses Continue during blocked cleanup even with a misleading Ready label. It grants no execution authority.

DTO copies, pins and validated requests retain measured reservations on the existing ledger. Ingress keeps the existing caps of 100 versions, 2,000 comments, 16 KiB text, 512 points, two minutes/note, 256 MiB voice audio and 256 KiB command envelopes. Original revisions/audio/ASR remain retained.

### Ownership rules

Each registration receives a checked, monotonic per-host `AttachmentId`. Detach never reuses an ID. `ForegroundOwner` records that exact attachment instance and the operation client string. Subjects remain issuance provenance and can repeat across attachments and roles. They grant no foreground ownership.

Every numbered request checks its operation client against the live manual lease before cache access, including Status and commands that will be refused. Manual commands with their own client field must also match the operation client. Successful unnumbered manual acquisition establishes the attachment binding even while the reply cache is empty. A different attached instance cannot use the slot even if it presents the same subject and client. Only successful replies enter the cache; refusals leave its bytes unchanged.

The no-lease rule is deliberately narrow. The same attachment and client can continue their retained operation stream. A successful `AcquireManual` can take over a slot from another attachment or client when no lease exists, regardless of the previous operation number. Numbered reads and other commands cannot make that transfer. Failed acquisition and malformed commands do not evict the old reply. Acquisition without a live lease bypasses a cached grant, so a revoked lease cannot be revived by replaying its old acquisition result. This prevents a lease-free Status squatter from blocking the next legitimate acquisition.

Owning detach with a live lease removes only the attachment binding. It keeps the client and retained reply. A newly issued Editor attachment presenting that same lease client can retry the lost operation, receive the original grant or Save payload, and bind the slot to its new instance. A successful unnumbered request, such as the reattachment Status probe, also establishes that binding while preserving the retained reply. Numbered requests from other clients are refused without changing the slot. Detach from any other instance leaves the slot untouched, including same-subject Viewer and Producer attachments through HTTP, direct-owner ingress, and MCP. Without a lease, owning detach clears the non-authoritative slot.

One additional guard closes the same rebinding path for unnumbered lease-renewal commands. A different attached instance cannot obtain an owned-media, interpretation, switch-confirmation, or barrier-confirmation lease reply and thereby change the foreground binding. This extends the lead's numbered-envelope rule because those successful replies also establish ownership. A real WAV admission witness covers this path. All rules use attachment IDs rather than role-specific detach branches, so future roles inherit the same isolation.
