## TE1.3 completion and commit scope

The feature is a separate new commit above the merge. No TE1.3 production
change is included in the merge commit.

`finish_task` accepts a task id and the observed timeline revision. Its first
ordinary H1 transaction stores the outer command identity, logical request
digest and original attempt. The host accepts completion only for a work turn
with settled children and deliveries, no pending question and no background
work. An unready request cannot reserve the parent's settlement identities.
Freeze and publication use the same issuer's next two identities. The host
reserves those identities on every public task Producer route.
An original substep receipt is reused before constructing any new envelope.
Each missing substep separately passes current attachment, endpoint, epoch,
grant, scope and ordinary-write admission. A receipt or completion status
never grants mutation authority.

The task's ingress gate drains before the freeze revision check. A later edit
cannot silently rebase the accepted completion. Publication uses the exact
frozen result and the existing host-owned accounting-reference binding.
Completion phases are freeze -> publication -> parent delivery -> settled.
A freeze alone is pending or blocked. Publication without applicable delivery
settlement is pending; only durable publication plus the parent's authenticated
observation, when required, is completed. Disposed delivery is blocked.
Substep failure retains the original successful outer intent outcome and
reports progress outside that immutable outcome. A failed progress read also
retains the acknowledged receipt and returns an explicit blocked/unavailable
status; it cannot replace the original outcome with a refresh error.

Live retries reuse original receipts and results. Stop or restart cannot revive
a task endpoint. Foreground reconciliation binds the original project, run,
task, attempt and command digest, and reads the retained facts without writing.
Trusted production reopen derives an explicit person-review block for an
unfinished completion or before-commit merge. It retains the frozen work and
manual merge envelope, disables Continue and refuses reservation/charging of
new native sends. The person must Stop and review before starting another run;
this implementation does not automatically merge after reopen. The new crash
witness uses the production restore and reservation paths, not the old private
merge-completion test helper.

Accepted edit-plan commits return the actual committed revision and a
conservative affected scope: operation names and JSON pointers derived from
the exact before/after document. Collection-size changes cover the collection;
projections exceeding 256 paths or 16 KiB cover the document root. A reporting
limit cannot turn an accepted commit into an error.

The role manifests append `finish_task` for Director, Editor-family and
Reviewer tasks. Their explicit schema goldens change; unrelated compact tools,
capability registry, instructions and full-wake goldens remain pinned. No
context/prefix rewrite, specialist setting, provider registration, terminal
capability, spending limit or accounting normalization changes are included.

### Completion and spending behaviour

Finish first tries to drain ingress under the host owner. An admitted edit
that is waiting for that owner causes `task_ingress_busy` before any intent
is accepted. A later finish can retry; the host never waits on an edit that
needs the host mutex. Once quiescent,
a logical fence blocks new edits through the revision check, intent commit
and freeze decision. A stale revision receives a durable non-applied
`StaleControl` receipt. Its task can still undo, redo and edit, and status
issues a fresh completion identity. No completion intent or substep identity
is reserved by that refusal.

Only the temporary, unapplied finish fence can reopen. Unknown publication
keeps its fence until exact-envelope reconciliation proves absence. An
accepted intent or successful freeze stays sealed. The accepted intent also
publishes the latest exact task history atomically, preserving acknowledged
edits and redo even if the process dies before freeze. Redo validates its
forward operations against the document before redo.

A permanent live completion failure installs a recovery block. It refuses
Continue, a new native reservation and pre-COMMIT charging of an already
reserved send. The last case has an otherwise-chargeable counterfactual and
checks unchanged accounting under the block. The task continues to report
Blocked if another finish clears the transient last-failure field.

Retryable normalized codes are `io`, `durability_unknown`, `unsettled`,
`save_in_progress`, `storage_backpressure`, `contention` and `cleanup_pending`.
`BundleError::Capacity` maps to `storage_backpressure`. Other failures enter
the permanent recovery state, including `run_limit`, changed revision or
history, lost authority, invalid payload/state and unsupported or damaged
data. Retry uses the same original finish and deterministic substep IDs.

A nonempty cached block list is intersected with freshly inspected durable
causes on each gating read. Completion and merge receipts therefore clear
the effective block in the same process. Receipt acknowledgements do not
depend on a redundant post-publication refresh.

### What the person can do

Muse's existing action did save the person's edit first, but directly making
an H1 task branch the manual branch left ordinary checkpoint publication
and manual authority unusable (`task checkpoint requires atomic H1 history
publication`). The fix reuses that Studio action and opens the exact task
history on a fresh plain manual branch. The original task branch, history,
frozen result and merge envelope remain bound to their original records.
The person can edit and Save after opening the recovered work.

Disclosure derives from retained H1 histories. It survives Stop and reopen,
including a completion that never froze, a pending merge and a separate
freeze/publication with no completion intent or merge envelope. Both
WorkingBranch and checkpoint selections require Stop and settled cleanup
for an H1 source. Repeating the selection preserves its original outcome.
The original pending merge remains refused after Stop, including after the
person's action; its original envelope and absent receipt remain unchanged.

At this head, normal production Director endpoint issuance after restore is
refused: no live Reserved attempt survives. GLM's `crash_director` helper
injects a new reservation. A valid live Director may merge before Stop under
the same host owner mutex. The person's selection requires Stop and settled
cleanup, so it cannot race that merge. The real reopen fixture checks the
production issuance refusal and retries the original merge before and after
owner recovery.

In both Studio modes, the path is: **Stop** the run, wait for cleanup, then
**File > Studio recovery and rescue…**. In the **Studio recovery and rescue**
window, choose **Save current edit, then open <branch>**, then confirm
**Save current work, then open recovery point**. Host mode obtains retained
work from HostStatus, since standalone refresh skips branch listing there.

The exact disclosure templates follow; angle-bracket placeholders stand for
the task, branch or path displayed by Studio.

- Before Stop: “Task <task> work is kept on working branch <branch>. Stop this run and wait for cleanup. Then choose Save current edit, then open <branch> to review it on your timeline. Your current edit is saved first.”

### Refused finish and uncertain completion substeps

Exact replay of a non-applied finish now reaches the same narrow reopen helper
as an absent finish. It requires no unresolved publication and no accepted
completion intent. Only `FINISH_UNCERTAIN` can become `OPEN`; accepted or frozen
ingress remains sealed. The witness injects a real `root_parent_sync` failure
through public dispatch, reconciles the durable stale refusal, performs real
Redo, Undo and a new edit, then completes with a fresh finish identity.

An uncertain nested freeze or publication retains the complete original finish,
the exact deterministic substep and its original immutable attachment identity.
The complete original request and attachment must match before namespace
reconciliation. After reconciliation the host checks the accepted outer receipt,
run, task, attempt, issuer/command identity, project, epoch, endpoint and grant.
A missing step still needs current live authorization. A committed step returns
its stored receipt; it does not regain live mutation authority because a
publication made the task terminal. The drive then uses the original fixed
substep identities and returns the original outer receipt.

The real MCP route performs this exact pending-finish check before role refresh:
an uncertain namespace cannot read the role projection. It accepts no fresh
finish or unrelated capability through that route. The original control's
attempt, owner epoch and expected candidate head are checked too. Terminal
replies retain the immutable outcome without minting new controls.

Real namespace faults cover freeze and publication, each both committed
(`root_parent_sync`) and definitely absent (`root_rename_io`). The tests pin the
actual receipt fate before retry, reject changed command/run/task/attempt and
