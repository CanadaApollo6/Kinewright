# Owner records beside operation history

H2a part 2 adds one owner facade in kinewright-project. Product readers continue using the existing records. The facade owns the Core history, approval ledger, baseline occurrence seeds, per-command origins and resource references. A role reservation precedes construction and covers its retained envelope; replay takes a separate workspace lease.

Callers provide a stable creation origin and optional approval when submitting an edit. Core prepares its atomic edit and reports effects before committing. The owner prepares its fallible metadata update from that event and the command payload. Both commit together. Undo, Redo and close change bounded command fates; they do not scan a document. Snapshot installation accepts only a validated owner snapshot and starts a new epoch without changing retained command keys.

Two shapes were considered. Keeping owner state outside the executor with a post-edit callback leaves a successful document mutation exposed when metadata refuses. Copying the entire owner state before each edit would repair atomicity but add document-sized lineage work. The chosen shape uses a preparation hook at the executor's existing transaction boundary and commits a bounded delta. Whole baseline metadata is rebuilt only at fold/install boundaries.

Lineage keeps one baseline seed map and stable origins attached to command identities. A boundary query replays document operations and lineage effects together from that baseline. No map per Undo/Redo boundary is retained. Resource references come from the baseline and each command's own payload. Reference counts permit dropping a payload only when it is discarded or transferred into an exactly scanned folded baseline. Independent immutable captures retain their own graph edges and reservation.

The stored owner record has baseline/current document edges, compact stack bytes, origins, seeds, resources and the approval ledger. Its snapshot identity is Core's canonical digest. The store object's content hash additionally binds owner metadata; it is not substituted for snapshot identity. Typed owner validation hooks run in Core's existing streaming validation pass.

The audit differential follows command fate. On 2026-11-13 the user exempted only the old target-satisfaction shortcut: a different command can make today's audit report an earlier discarded approval kept. Tests must explicitly recognize that cause, count it and require a nonzero count. No second approval-satisfaction answer is added. H2b receives an inventory of readers consuming that old answer.

Owner preparation and lineage-query scratch are charged inside Core's replay workspace, not added on top of its peak. The owner reserves twice A before Core copies/applies; recorded step peaks exclude that temporary reservation. Thus retained R plus one admitted W still bounds the transaction. Fixed full-role leases make ordinary growth local; multiple histories, captures and simultaneous workspaces still share the role-wide ledger.

Do approvals retain their original key and payload digest across epochs. Installing a selected snapshot recomputes their fate from exact installed commands or the snapshot's matching baseline fact; a disappeared command is discarded, while the same command restored by the snapshot can be applied again. A fixed optional epoch records the last installation that changed the fate. Recreation is one sticky bit per approval, set from later accepted creation identity effects; it never makes a discarded command kept.

Undo/Redo approvals use the consent's own id, a direction and fixed step evidence: first command key and digest, command count, and an ordered digest of every command key and digest. Core mints no command for an approval. Undo holds while those commands are not applied, and reverses when they are applied; Redo holds while applied, reverses while undone, and is discarded when absent. Exact prefix matching permits a longer installed step, while an incompatible shape is uncertain; ordinary Redo closes its gesture, so the following edit cannot extend that step. There is no stored approval fate flag.

A record carries an exclusive, fixed-size fold frontier and at most one terminal fact per approval target. An absent target older than the installed frontier with no matching evidence reports `Uncertain(MissingFoldProvenance)`; known folded/discarded facts and absent newer targets retain exact answers. The selected snapshot owns those facts. Uncertainty is kept separate from held, reversed and discarded counts. H2b readers which need an exact answer can inspect the installed document through the target step's identity effects; that document check is intentionally absent here. An analogous pre-approval folded snapshot for a Do approval cannot arise: the approval and Do acceptance are one transaction, so a later fold snapshot already contains its approval evidence.

Do and transition approvals share the run's 256-entry cap. A transition's structural charge is 1,024 bytes plus the actual capacity of its consent id digest (normally 64 bytes), including its eventual terminal fact; 256 entries charge 278,528 bytes. Decode reserves 16,384 bytes per transition, or 4 MiB for 256. These charges remain inside A and W, rather than adding an unbounded journal. Core's operation-kernel validation, duration and identity passes are unchanged and counted separately from the history and owner work.

A folded Do fact also carries a fixed prefix stamp ending at that approved command. It can settle a later transition approval only when the stamp matches the complete target evidence; individual folded keys alone cannot prove the required step prefix. There is still at most one such fact per Do approval, precharged in its 768-byte fixed allowance. This avoids both unnecessary uncertainty when a matching proof exists and a false held answer when the same command was inside a differently grouped step.

Owner construction and open enforce the role's policy: Ordinary folds; Task and Candidate never fold. A task record cannot silently change the pinned-base delta into a folding history. Fold frontiers obey both epoch/key order and the globally monotonic accepted position. The optional complete operation recorder remains available on the standalone Core history for evaluation; H2b still decides its owner/wiring at the switch.
