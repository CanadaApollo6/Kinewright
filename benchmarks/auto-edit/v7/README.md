# Kinewright Audio Workflow v7

Benchmark id `kinewright-audio-workflow-v7`. Contract: [`docs/AU6-WORKFLOW-EVALUATION.md`](../../../docs/AU6-WORKFLOW-EVALUATION.md).
Scenario authority: `kinewright_core::au6_scenarios`. Source generator: `kinewright_media::au6_sources`.

**Status: pending real-harness run.** Nothing in this directory records a measured
model result yet. CI runs the suite's *unit* tests — construction, packaging, the
manifest/ground-truth binding — and never runs a model. There is no published v6
result to compare against, and this suite does not pretend otherwise.

## What this suite proves

Six named audio workflows, one model turn each, over the AU1–AU5 surface:

| id | Scenario | What the model is asked to do |
| --- | --- | --- |
| `a1` | (a) two-person interview | Match two voices, group them, and ride the bed out of the way without pumping. |
| `a2` | (b) uneven podcast | Bring two guests to one level, tame the loud one's swing, and clean the hard edit. |
| `a3` | (c) noisy location dialogue | Fill the cut gap with the room's own tone, then clean hiss, hum and clicks. |
| `a4` | (d) event multicam | Cut the two angles, mute the cameras' scratch audio, and leave the recorder alone. |
| `a5a` | (e) EBU R128 delivery | Deliver the interview as a broadcast master and report what it measured. |
| `a5b` | (e) streaming delivery | Deliver the interview for a streaming platform and report what it measured. |

Every prompt names the tracks and the intended outcome and **never names a
parameter or a value**: the point of the suite is to find out whether the model
can choose them.

This suite is the *model* lane. The same five scenarios are discharged
objectively by ordinary `cargo test` fixtures (AU6 §4) and by scripted MCP
end-to-end tests (AU6 §5). **The technical gates do not need this suite**, and a
failure here is a statement about a model, not about the mix engine.

## Fixtures

No fixture bytes are checked in. `manifest.json`, `ground-truth.json` and this
file are the only files in this directory.

Every buffer is authored in Rust from `au6_scenarios`' analytic values and
written at fixture time by `kinewright_media::au6_sources` — the *same*
generator the technical gates use, so a buffer cannot drift between the two
claims made about it. `a3` additionally saves its project into a temporary
directory; it is the only task whose `PreparedFixture` carries a `project_path`,
and without one `capture_room_tone` refuses `project_not_saved` and the task is
unsatisfiable.

`ground-truth.json` carries, per scenario, the **canonical document** —
`canonical_document`, the tracks, clips and buses that `au6_canonical_operations`
leaves when it is applied to that scenario's initial document — beside the batch
itself and the expected measurements. It is **generated**, never hand-edited: it
is written by `au6_ground_truth_json` in
`crates/kinewright-agent/src/bin/kinewright-eval.rs` and
`published_v7_manifest_tracks_the_audio_workflow_suite` asserts the checked-in
bytes equal the generated bytes. There is deliberately no environment knob to
regenerate it — when the two diverge the test prints the generated bytes and the
implementer pastes them, so a ground-truth change is always a reviewed edit.

## How to run it

```sh
source ./scripts/setup-ffmpeg.sh
KINEWRIGHT_EVAL=1 cargo run -p kinewright-agent --bin kinewright-eval -- \
  --suite audio-workflow-v7 --harness claude-code --samples 3
```

`--only a3` runs one task. `--samples 3` is what the acceptance target below
asks for. The run writes `target/evals/<run-id>/` containing `results.jsonl`,
`machine-report.json`, `artifacts/`, `human-review.json`, `blind-key.json`, and
`blind/`.

The unit tests, which is all CI runs:

```sh
cargo test -p kinewright-agent --bin kinewright-eval
cargo test -p kinewright-agent --lib
```

## The blind review procedure

The reviewer is handed **`blind/` and nothing else**, and opens **only**
`blind/review-form.json` plus the `blind/<blind_id>.png` and
`blind/<blind_id>.mp4` artefacts beside it.

**Listen to the `.mp4`.** That is the reviewer's artefact. The `proof.png` is a
still of a flat 320×180 test raster and is of no use to a listener; it is kept
because the blind listing shape requires it.

There is no loudness-matched A/B hold in the product, so every artefact is
heard at whatever level the reviewer's player produces. Use **one listening
level for the whole package**.

- **Do not open `machine-report.json`.** It carries every machine verdict.
- **Do not open `blind-key.json`.** It is written to the run root, deliberately
  outside `blind/`, and it is what maps a `blind_id` back to a task.
- **Do not open `results.jsonl`, `human-review.json`, or `artifacts/`.**

The form is keyed on `blind_id` alone — a 12-hex prefix of the artefact digest —
and carries no task id, run id, benchmark id, harness, model, machine verdict,
assertion name, parameter name or parameter value.
`au6_the_blind_package_discloses_no_machine_provenance` scans both the `blind/`
listing and the form's bytes for all of those and is proved able to fail on
each.

For every entry, rate `audio_finish` and `delivery_readiness` on the 1..=5
scale in 0.5 increments, answer every question in `questions`, and set
`accepted`. `story`, `pacing`, `visual_finish` and `captions` are pre-marked not
applicable: the audio suite is judged on balance and intelligibility, and
rating the rest would be fabrication. Two byte-identical artefacts share one
`blind_id`, so one viewing scores both rows. `a5a` and `a5b` are two distinct
encodes of one document and therefore two `blind_id`s.

Score the filled-in form with:

```sh
cargo run -p kinewright-agent --bin kinewright-eval -- \
  --score-review target/evals/<run-id>/blind/review-form.json
```

`--score-review` resolves each `blind_id` through the sibling `blind-key.json`
**before** the artefact bindings are checked, writes the unblinded
`human-review.json` into the run root, and refuses a `blind_id` the key does not
carry with a typed error naming it. A form presented without its key is a typed
error naming the missing path, never a silent fallback.

**What is deliberately not blinded: the scenario identity.** It is inherent in
the question being asked — *"Is the dialogue clearly balanced above the music
bed?"* *is* the interview — and a two-voice-plus-bed programme is recognisable
in three seconds. AU6 blinds the machine provenance and says plainly what it
does not blind. A reviewer who opens `blind-key.json` is unblinded; that part is
procedure, not something a test can bound.

## The human gate (AU6 §8.6)

For **each** task in the package:

> each passes **3/3** model samples against its technical gates; at least **2 of
> 3** outputs are accepted by a person; **every question is answered**; and the
> mean human rating is at least **4.0/5** over the applicable dimensions, N/A
> dimensions excluded. **One success does not satisfy the slice.**
